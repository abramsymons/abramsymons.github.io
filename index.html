Ordering Before Execution

Eight years in decentralized systems, one idea, told in the order it happened.

Bitcoin taught us the blockchain. I think the next step is to see the blockchain for what it is: a replicated state machine. For eight years in decentralized systems, my work has come down to one question. How do many machines that don't trust each other end up with the same state?

My answer has been the same since 2018. Agree on the order of events first. Let each application execute them itself. Then make that agreement as cheap and as safe to verify as possible. The first part of this page explains why I think that beats today's blockchains. The second part is how I arrived at it, one project at a time.

Part one · The argument

A blockchain is one state machine shared by every app

A blockchain does one useful thing very well: it keeps many untrusting machines in agreement. But it bundles that with everything else. Every app on Ethereum runs on every node, on the same CPU, writing to the same state, secured by the same stake. Every app waits in the same queue.

The two usual fixes keep something shared

Solana makes the shared machine bigger: many cores and many disks, with transactions that don't touch the same state running in parallel. It's faster, but every app still lives in the same state on the same nodes. Layer 2s move execution onto separate chains, but they still settle to a shared L1 state and borrow its stake. Each fix removes one bottleneck and keeps the others.

Share only consensus

The step I took with Zellular was to share the one thing that really has to be shared, the order of transactions, and nothing else. Each app runs as its own BFT service with its own CPU and its own state. A sequencer gives every replica the same ordered log with a compact finality proof, and each replica executes it. Security is bought per app, or even per request, from restaked operators on EigenLayer. An app that holds little value doesn't pay for the security of one that holds billions.

Shared security, not shared state.

What follows from that is the part developers care about. Apps can be written in Python, JavaScript, Go or any other language instead of Solidity or Rust. An existing Web2 service can become decentralized with small changes: users sign their requests, requests go through the sequencer, and the business logic stays as it is. Throughput stops depending on how fast one global machine can execute everything. With batching, it depends mainly on the leader's bandwidth. A 25 Gbps leader can carry about a million 100-byte transactions per second.

I like to compare it to web frameworks. A blockchain is Django: a full stack that decides your language, storage and execution model for you. Zellular is Flask: the one essential piece, done well, and everything else is your choice. Simple designs are also easier to verify, which matters when they hold money.

Then everything else becomes a service

Once apps are replicated state machines, the hard shared problems can be offered as decentralized services they compose, so developers write only their own logic. Over the years I've designed each of these.

  • Consensus as a serviceZellular, and now vseq on Firedancer's Alpenglow.
  • Custody as a serviceMulti-chain FROST custody from one validator group.
  • Orderbook as a serviceZex, an exchange engine replicated across nodes.
  • Oracle as a serviceMuon, with threshold, optimistic and shield security layers.

Part two · How I got here

entry 02018 – 2023

BrightID and the first replicated log

Core team developer, BrightID

BrightID lets people prove they use only one account, through a social graph of real connections. It grew past 73,000 verified users, and Gitcoin Grants was among the 15 apps that used it. I was the primary architect and developer of the node that stores the graph, with more than 600 commits.

The core problem was keeping many independent nodes in agreement about the graph. Putting every new connection on Ethereum mainnet would have cost users too much gas, and sidechains and L2s didn't exist yet. So we launched IDChain, a dedicated proof-of-authority chain, and I designed the nodes to read graph operations from it and replay them in block order. Every node reached the same graph without trusting the others. Looking back, that was my first replicated state machine with ordering separated from execution.

I also led the anti-sybil research: SybilRank variants, a group-based ranking algorithm, a simulator for attacking the graph, and Bitu, a clustering-based verification about 12,000 users had reached by 2022. When our CEO wanted stronger privacy, I designed and built blind-signature verifications, so an app can confirm someone is verified without anyone linking their accounts across apps.

What stayed with me: if every replica sees the same operations in the same order, consensus and execution can live apart.

entry 12021 – 2023

Muon: an oracle as a service, in layers

Architect, then technical lead, Muon Network

Muon began as a decentralized price oracle for DEUS and Symmio. I designed its architecture in 2021 and chose threshold signatures from the first day. With multisig, the cost of verifying on-chain grows with every signer. With a threshold Schnorr signature, hundreds of nodes produce one signature that costs the same to verify no matter how many signed. MPC was still rare in crypto then.

Threshold signatures were only the first layer. I designed Muon as modular security an app can stack. The optimistic layer is economic: a warrantor node answers quickly but locks collateral behind each response, supervisor nodes re-check the data and open disputes, and a DAO slashes anyone who lied. The shield adds an independent party that re-verifies each event before co-signing. If the shield misbehaves it can only stop the flow, never forge data.

In 2022 I joined the team directly to help with security. The JavaScript node had grown large and complicated, and I concluded that a lean rewrite in Python was safer than auditing it. I led about six engineers through it and taught them the FROST protocol. I also filed fourteen security and design issues, including a rogue-key attack on the key generation. The network reached more than 3,400 testnet operators and a mainnet of over 1,500 nodes. Some problems couldn't be solved inside an oracle, so I left to build Zellular.

What stayed with me: make the trusted part small enough to verify, and give each kind of failure its own layer.

entry 22023 – 2025

Zellular: consensus as a service

Founder and protocol architect, Zellular

Zellular turned the argument above into a product. I designed the protocol: a leader-based BFT design with no proposer rotation and no gossip, BLS-aggregated finality proofs over a chain of batch hashes, and a dispute path for replacing a faulty leader. Nodes post users' signed requests to the sequencer, and every node receives them back in the same order.

We launched on the EigenLayer testnet in September 2024 with about ten operators and sub-second finality. Once batching took consensus out of the way, the next bottleneck was checking users' signatures, and we pushed that to 750,000 verifications per second on four GPUs. To make EigenLayer usable beyond Go, we wrote SDKs in Python and JavaScript with reference services. They won 1st place at EigenLayer's AVS MicroHacks in 2024 against more than 100 builders, and the Eigen Foundation later gave Zellular a 100,000 EIGEN ecosystem grant.

The second service was custody. I wrote the pyfrost protocol specification, which works through secret sharing, distributed key generation and the rogue-key attack, and shows how naive complaint handling lets two colluding nodes push honest ones out. From there I designed zbtc, a Bitcoin bridge secured by restaked operators, and EigenSync, built at ETHGlobal Superhack 2024, which makes those operators' signatures verifiable on any EVM chain. Both stayed prototypes, but together they became a general multi-chain custody service.

What stayed with me: share only what must be shared. Ordering and custody are those things.

entry 32024 – now

Zex: an orderbook as a service

Founder and protocol architect, then tech lead and reviewer, Zex

Zex started as the proof that the argument works: an exchange replicated as a state machine on Zellular. We announced it in July 2024, matching over 100,000 orders per second with sub-second finality and cross-chain trading. It grew faster than Zellular itself, mostly because that's where the money in DeFi was, and in 2025 Zellular merged into it. I handed the business to a dedicated team, appointed a CTO, and stayed on as tech lead and reviewer.

The custody service became ZexPorta. One validator group controls funds on every chain. On Bitcoin, each user gets a Taproot address by tweaking the group key, and a withdrawal looks like an ordinary single-signature spend. On EVM and Tron, deposits land in CREATE2 contracts and a Schnorr verifier checks the threshold signature. Solana and Aptos verify Ed25519 natively. An independent shield key must co-sign every withdrawal, so even a compromised threshold group can't move funds. For production we replaced pyfrost's own cryptography with the Zcash Foundation's audited FROST. I also designed wallet-free login, where every replica checks a Google-signed token bound to the user's session key, the same approach Aptos and Sui use for keyless accounts.

Now I'm moving Zex onto production-grade cores. vseq runs Firedancer's implementation of Alpenglow, Solana's new consensus, as a standalone ordering service, so any app can get a production consensus engine without running Solana. For the matching engine, I redesigned the protocol so independent implementations agree exactly, then we built a C engine and checked it against the Python one batch by batch. It reaches about a million orders per second, ten times the original target. I design these systems and direct AI-assisted implementations in languages I don't write daily, such as C.

What stayed with me: build your own version to learn, then stand on audited cores before you hold anyone's money.

entry 4ongoing

Breaking consensus, including my own

Security research

Designing consensus taught me where it breaks, so I look for those breaks in other chains, with AI-assisted review as part of my workflow. On Aptos I found a High-severity consensus bug that could halt the network, which earned a $30,000 bounty, plus three more valid findings that turned out to be duplicates. On Sui I've reported eight issues. Six denial-of-service findings were confirmed as duplicates, four of them reachable by unauthenticated peers, and two are still under review.

I hold my own systems to the same standard. I audited Zex's custody stack by hand, the threshold-signing service and the deposit and withdrawal code for every chain, and wrote up 17 findings, several of them critical, in key generation, signing and deposit detection.

What stayed with me: a duplicate still means you were right. The next step is to be first.

What I keep relearning

  1. Share only what must be shared. Usually that's ordering.
  2. Never trust a single path: a threshold of signers, collateral at stake, or a co-signing key.
  3. Make the trusted part small enough to verify.
  4. Prototype your own design to understand it, then ship on audited, production-tested cores.
  5. Doubt your own numbers until something independent confirms them.
