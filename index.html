Ordering Before Execution

For eight years I've worked on one question: how do many machines that don't trust each other end up with the same state? My answer hasn't changed since 2018. Agree on the order of events first, and let each application execute them itself.

Why I build this way

A blockchain is a replicated state machine that every app shares. Every app on Ethereum runs on every node, competes for the same CPU, writes to the same state and relies on the same stake. It's one phone booth for a whole city, and every app waits in the same queue.

I think an app is better off as its own replicated state machine. The nodes that run it agree on the order of requests, and each one executes them and arrives at the same state. How that order is agreed is a separate, replaceable part. It can run on the same nodes that hold the state, or come from any consensus provider that fits the app. What matters is that ordering and execution stay apart.

Developers gain the most from that. Apps can be written in any language, not only Solidity or Rust. An existing service can become decentralized with small changes: users sign their requests, the requests get ordered, and the business logic stays the same.

It also changes what limits an app. A blockchain runs every app on the same machines, so they all compete for the same capacity. When each app has its own replicas, apps scale independently, and a busy app doesn't slow down anyone else. Each app can also drop the generality a blockchain has to carry. A general-purpose chain must be ready for any contract anyone might deploy, so every transaction pays for a virtual machine, gas metering and rules that exist for other apps. An app with its own state machine defines only the transactions it needs and executes them directly. On Zex's hot path there are only three: buy, sell and cancel. That is a large part of why it can be both simpler and much faster.

Once ordering is its own piece, the other hard parts of a decentralized app can be separated out the same way. Over the years I've designed four of them: consensus, custody, an orderbook, and an oracle. This is how each one came about.

BrightID: the first replicated log

2018 – 2023 · core team developer

BrightID lets people prove they use only one account, through a social graph of real connections. It grew past 73,000 verified users, and Gitcoin Grants was among the 15 apps that used it. I was the primary architect and developer of the node that stores the graph.

The problem was keeping many independent nodes in agreement about the graph. Putting every connection on Ethereum would have cost users too much gas, and L2s didn't exist yet. So we ran our own proof-of-authority chain, IDChain, and I designed the nodes to read graph operations from it and replay them in block order. Every node reached the same graph without trusting the others. That was my first replicated state machine with ordering separated from execution, before I had a name for it.

I also led the anti-sybil research, implemented the Bitu verification model, and designed blind-signature verifications, so apps can check that a user is verified without linking that user's accounts across apps.

Muon: an oracle as a service

2021 – 2023 · architect, then technical lead

Muon started as a decentralized price oracle for DEUS and Symmio. I designed it around threshold signatures from day one, when MPC was still rare in crypto. With multisig, on-chain verification gets more expensive with every signer. With a threshold Schnorr signature, hundreds of nodes produce one signature that costs the same to verify however many signed.

I treated security as layers an app can combine. Threshold signatures give cryptographic security. An optimistic layer gives economic security: a node vouches for a response with locked collateral, other nodes check it and can dispute it, and a liar loses its collateral. A shield lets an independent party re-check each event and co-sign; if the shield misbehaves it can only stop the flow, never forge data.

In 2022 I joined the team directly. The JavaScript node had become too complex to audit with confidence, so I led about six engineers through a lean rewrite in Python and taught them the FROST protocol. Signing latency fell from about seven seconds to under one. Muon grew to over 3,400 testnet operators and a mainnet of more than 1,500 nodes. Some of the problems I cared about didn't fit inside an oracle, so I left to build Zellular.

Zellular: consensus as a service

2023 – 2025 · founder and protocol architect

Zellular was my first attempt to offer ordering as a service, secured by restaked operators on EigenLayer. I designed a leader-based BFT protocol whose only job is ordering: no proposer rotation, no gossip, finality proven by aggregated BLS signatures over a chain of batch hashes, and a way for nodes to replace a faulty leader. It ran on the EigenLayer testnet with sub-second finality. Once consensus was out of the way, the next limit was checking users' signatures, and we pushed that to 750,000 verifications per second on GPUs.

To make EigenLayer usable outside Go, we wrote SDKs in Python and JavaScript. They won first place at EigenLayer's AVS MicroHacks in 2024, and the Eigen Foundation later gave Zellular a 100,000 EIGEN ecosystem grant.

The second service was custody. I wrote the pyfrost specification for distributed key generation and threshold signing, including an analysis of how naive complaint handling lets two colluding nodes push honest ones out. That grew into prototypes for a Bitcoin bridge and for verifying EigenLayer operators' signatures on any chain, and then into a general custody service that holds funds on many chains with no single key holder.

Zex: an orderbook as a service

2024 – now · founder and protocol architect, then tech lead and reviewer

Zex began as a demo of the whole idea: an exchange running as a replicated state machine on Zellular. It grew faster than Zellular, because that's where the demand was, and in 2025 Zellular merged into it. I handed the business to a dedicated team and stayed on as tech lead and reviewer.

The custody service became ZexPorta. One group of validators controls funds on Bitcoin, EVM chains, Tron, Solana and Aptos, each chain with its own way of verifying the same kind of threshold signature. An independent key must also approve every withdrawal, so even a compromised validator group can't move funds. I also designed login without wallets or custodial providers, the same approach Aptos and Sui use for keyless accounts.

Now I'm moving Zex onto production-grade parts. We replaced our own threshold cryptography with the Zcash Foundation's audited FROST. vseq runs Firedancer's implementation of Alpenglow, Solana's new consensus, as a standalone ordering service. The Python matching engine I first prototyped handled about 100,000 orders per second. When I came back to it in late 2025, a period of feature work had pushed throughput down to around 10,000, and I brought it back above 100,000 by removing bottlenecks in the engine, the export pipeline and the API services. Then, with the protocol proven, a few small changes made an exact C port practical. Checked against the Python engine batch by batch, it reaches up to 6 million orders per second on simple loads and about a million on a realistic deep order book. I design these systems and direct AI-assisted implementations in languages I don't write every day.

Breaking consensus and custody

ongoing · security research

Designing consensus taught me where it breaks, so I look for those breaks in other chains. On Aptos I found a high-severity consensus bug that could halt the network and received a $30,000 bounty. On Sui I've reported denial-of-service issues, several reachable by anyone on the network. I also contributed to Zex's internal security audit, reviewing the custody service's key generation, signing and deposit handling ahead of launch.

What I keep relearning

  1. Simplicity is the root of both security and performance. Start with the simplest version that proves the idea, then make it production-ready.
  2. Keep ordering and execution apart, and treat consensus as a part you can replace.
  3. Never trust a single path: use a threshold of signers, collateral at stake, or a second key.
  4. Keep the trusted part small enough to verify.
  5. Build your own version to learn, then ship on audited, production-tested parts.
